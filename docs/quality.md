# Quality: Kit Harness Protocol

This file applies to people and AI agents contributing to KHP. Tests are
the spec: `features.yaml` and each case's `intent` state the expected
behavior. When code and a case disagree, the case wins unless a maintainer
approves changing it.

## Local checks

Use Node.js 22.18 or later and pnpm 10. From the repository root:

```sh
pnpm --dir tools/conformance install --frozen-lockfile
pnpm --dir tools/conformance build
pnpm --dir tools/conformance typecheck
pnpm --dir tools/conformance test
```

The Python example requires Python 3.11 or later and the dependencies in
`examples/docx-python/requirements.txt`. See its
[setup and conformance instructions](../examples/docx-python/README.md).

The gating tests can be executed directly from the repository root:

```sh
node --test tools/conformance/test/harness.test.ts
node --test tools/conformance/test/cli.test.ts tools/conformance/test/containment.test.ts
"$KHP_PYTHON_ENV/bin/python" -B examples/docx-python/test_example.py
```

The Python case's `python3` must resolve to an interpreter with those
dependencies installed when executing its `case.yaml` command. No generic
case runner is included in this repository. These gating tests call no
model. Only a maintainer starts real-model `layer: eval` cases.

Before finishing any task, run this scan and report its real exit code:

```sh
! grep -rIlE '/(Users|home)/[a-z]' --exclude-dir=.git --exclude-dir=node_modules --exclude-dir=dist .
```

The task is not done until it exits 0. Claude Code runs the same command
through `.claude/hooks/quality-gate.sh`; agents without hooks run it by
hand. `KITION_SKIP_QUALITY_HOOK=1` is a session-only emergency bypass; any
use must be disclosed.

## Feature catalogue and cases

`features.yaml` is the catalogue. Each feature has a stable id, title,
dimensions, priority, status, source paths, case ids, and an added date.
Its `gap` describes what is missing. A feature with `status: has` must work
end to end; a partial feature has cases for what is implemented. Any
`FEATURES.md` generated from the catalogue must not be edited by hand.

Cases live at `cases/<feature-id>/<case-slug>/case.yaml`; regressions live
at `cases/regressions/issue-<n>/case.yaml`. Feature ids use lowercase
dot-separated segments; case slugs use lowercase letters, digits, and
hyphens. The case's `id` equals its path under `cases/`.

Each case declares:

- `format: 1`, `id`, `feature`, and an `intent` explaining the guarantee.
- A `layer` (`unit`, `gate`, `corpus`, or `eval`) and optional `dimension`.
  Gating tests are deterministic and run before a task finishes; corpus
  cases need separately obtained inputs; eval cases need a maintainer's launch.
- `source`, including `kind`, `from`, and `license`. Inputs must be
  synthetic, owned, or redistributable. User files need recorded consent.
- `input`, `steps`, at least one `expected` entry, and `since`.
- Optional `reference`, `tolerance`, `tags`, `requires`, and `timeout_s`.

This repository's gating tests use `exec: { cmd: [...] }` and an `exit`
expectation with `value: 0`. Commands run from the repository root; they
must fail when the promised behavior is broken. Gating tests have a
default timeout of 20 seconds and a hard cap of 60 seconds. The total
gate budget is `gate_budget_s`, at most 600 seconds. A missing required
tool is a failure, never a skip. Run outputs belong in temporary folders
or `target/gate/<case-id>/`, never in case inputs or expected results.

Each input is at most 512 KB, each expected PNG at most 50 KB, each case
directory at most 1 MB, and all case inputs at most 50 MB. Larger inputs
belong to a separately obtained corpus.

## Expected results are protected

Only a maintainer approves changes to:

1. Every file under `cases/**/expected/`, including additions, deletions,
   and renames.
2. Every path matched by `protected` in `features.yaml`.
3. An existing case's `expected`, `tolerance`, `reference`, `input`, or
   `steps`; moving a case from `gate` to another layer; deleting or moving
   the case directory.
4. Removing a feature that has cases or lowering its priority.

Never change expected results to make a test pass. If a result appears
wrong, stop and explain why; only a maintainer can approve a change. External
references are never regenerated by a tool. A self reference may be
regenerated only with maintainer approval, recorded in a commit message as
`Expected-Change: <case-id>: <reason>`. Newly added expected results also
need review against their named reference.

Never weaken tests: no deleted or loosened assertions, raised tolerances,
added `#[ignore]`, `.skip`, `.only`, or `.todo`. Inspect the diff of cases,
catalogue, and test files before committing, and report any protected
change to the maintainers. No expected-result changes may be merged
automatically.

Every bug fix starts with a failing regression case, then the fix. Every
new feature adds a catalogue entry and at least one gating test. Stage
only files you changed, by name, because other contributors may share the
checkout. Do not publish local paths, credentials, internal planning
material, or unpublished research in the tree.
